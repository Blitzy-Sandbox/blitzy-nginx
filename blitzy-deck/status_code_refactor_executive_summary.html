NGINX HTTP Status-Code Registry Refactor

Centralized, RFC 9110-compliant status handling — Executive Summary

Registry + Facade API · single source of truth · zero wire-behavior change

The Problem

Status-code knowledge is dispersed across four locations:

  • ~44 modules mutate r->headers_out.status directly
  • A separate reason-phrase table (ngx_http_status_lines[]) lives in the HTTP/1.x header filter
  • Numeric #define NGX_HTTP_* constants sit in ngx_http_request.h
  • Duplicated error fragments in special_response.c

Risk Inconsistency, hard to extend, no central validation.

Objective

  • Consolidate behind one immutable registry plus a thin 5-function facade
  • Zero wire-observable behavior change — additive, dual-path coexistence
  • Opt-in RFC 9110 §15 validation, gated at compile time
  • 100% backward compatibility — existing constants & direct assignment still work

Patterns applied: Registry, Facade, immutable / read-only-after-init (lock-free), direct/offset-indexed O(1) lookup, compile-time feature flag, pass-through guard.

The write path is funneled through ngx_http_status_set() into one registry, while HTTP/1.x, HTTP/2 and HTTP/3 encoders keep reading the unchanged r->headers_out.status field — cross-protocol consistency with no encoder edits.

The Registry — Single Source of Truth

A single immutable static const ngx_http_status_def_t status_registry[] hosted in src/http/ngx_http_request.c is the authoritative record of every status code.


typedef struct {
    ngx_uint_t    code;
    ngx_str_t     reason;
    ngx_uint_t    flags;
    const char   *rfc_section;
} ngx_http_status_def_t;

Offset-indexed O(1) lookup · branch-predictable · zero allocation · lives in read-only .rodata · < 1 KB · reuses existing reason phrases.

The Facade API — 5 Functions

FunctionPurpose
ngx_http_status_setSet response status through the facade (guard + assign)
ngx_http_status_validateCheck a code against RFC 9110 §15 (opt-in strict mode)
ngx_http_status_reasonResolve the default reason phrase for a code
ngx_http_status_registerCompile / init-time registration of new codes
ngx_http_status_is_cacheableReport heuristic cacheability (RFC 9111)

All declared in src/http/ngx_http.h; each function ≤ 50 lines (excluding comments).

Before / After — Call Site


// OLD
r->headers_out.status = NGX_HTTP_NOT_FOUND;

// NEW
if (ngx_http_status_set(r, 404) != NGX_OK) {
    ngx_log_error(NGX_LOG_ERR, r->connection->log, 0, "invalid status code: 404");
    return NGX_HTTP_INTERNAL_SERVER_ERROR;
}

No new #include needed — the facade is declared in the umbrella ngx_http.h that every HTTP module already includes.

Cross-Protocol Unification

  • The HTTP/1.x, HTTP/2 and HTTP/3 filters remain read-side consumers of the unchanged r->headers_out.status field
  • Centralizing the write through ngx_http_status_set() unifies emission across all three protocols
  • No encoder edits — the HPACK and QPACK :status paths are untouched

Status is finalized before ngx_http_top_header_filter; there are no filter-API changes.

Safety — Sentinels & Upstream

  • Internal sentinel codes 444 and 494–499 are non-wire-emitted and whitelisted by ngx_http_status_validate
  • Responses where r->upstream is set bypass strict validation via the pass-through guard
  • No upstream status transformation, ever — origin-assigned codes are never rewritten

Opt-in Validation

  • Configure with --with-http_status_validation → compile macro NGX_HTTP_STATUS_VALIDATION
  • Delivered via -DNGX_HTTP_STATUS_VALIDATION in CFLAGS (no auto/options wiring required)
  • Permissive default: when disabled, ngx_http_status_set() compiles to the same single store — zero overhead

Classification flags: NGX_HTTP_STATUS_CACHEABLE, NGX_HTTP_STATUS_CLIENT_ERROR, NGX_HTTP_STATUS_SERVER_ERROR, NGX_HTTP_STATUS_INFORMATIONAL.

  • All NGX_HTTP_* constants retained; direct r->headers_out.status assignment still works
  • ABI preserved — the NGX_MODULE_V1 module interface is unchanged; third-party modules keep building & loading
  • error_page parsing and per-protocol normalization preserved exactly
  • Graceful binary upgrade — a new binary against an existing configuration works

Approved Additive, dual-path coexistence — not a destructive rewrite.

Standards Grounding

  • §15.2 — 1xx Informational
  • §15.3 — 2xx Successful
  • §15.4 — 3xx Redirection
  • §15.5 — 4xx Client Error
  • §15.6 — 5xx Server Error

RFC 9111 — heuristically cacheable

Marked by NGX_HTTP_STATUS_CACHEABLE:

200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414, 501
