Executive Summary · Project: blitzy-nginx
01

The Problem

Status handling is scattered

Today, HTTP status codes are set, propagated, and rendered by three independent mechanisms — with no single owner and no place to enforce correctness.

Direct assignment

Writers set the status field directly at 17 sites across 14 files.

Return-based flow

Handlers return status codes that funnel into the error-page path.

Private reason table

Wire text like 200 OK comes from a hand-maintained lookup table.

14files touched
3independent owners

Why it matters

Scattered ownership creates real business risk as the platform evolves.

No single source of truth

Status knowledge lives in three places, so changes must be made — and audited — in every one.

Nowhere to enforce RFC 9110

There is no seam at which HTTP correctness can be validated.

Duplicated logic

Reason phrases and would-be validation rules are repeated rather than shared.

Harder to audit and evolve

Every new behavior multiplies across the scattered call sites.

02

The Solution

One authoritative status API

Five small functions become the single, sanctioned way to work with HTTP status.

ngx_http_status_set()

The single sanctioned way to set a response status.

ngx_http_status_reason()

The single source of human-readable status text.

ngx_http_status_validate()

Optional RFC 9110 compliance check.

ngx_http_status_register()

Seeds the registry once, at startup.

ngx_http_status_is_cacheable()

Quick cacheability answer from metadata.

A registry with RFC 9110 metadata

One static table holds, per status code, its number, its reason phrase, class flags, and an RFC 9110 §15 section reference.

1xx Informational 2xx Successful 3xx Redirection 4xx Client Error 5xx Server Error
O(1)array-index lookup
< 1 KBper worker
read-onlyafter startup

Target: every write flows through ngx_http_status_set(); the HTTP/1.x header filter resolves its reason phrase through ngx_http_status_reason(), both against one static registry. HTTP/2 (HPACK) and HTTP/3 (QPACK) carry no reason phrase, so they emit the numeric :status directly. Validation is compiled in only when --with-http_status_validation is set; upstream codes pass through unvalidated.

Benefits & Compliance

What we gain

RFC 9110 compliance

Grounded in the current HTTP semantics standard, with class metadata and section references built in.

Single source of truth

One write seam and one reason seam replace three independent owners.

Predictable performance

Direct array index, no locks, under 1 KB — a hot-path with a tiny, fixed cost.

Opt-in validation

Turn on strict RFC checking only where and when it is wanted.

Nothing breaks

The change is additive. Existing code, builds, and deployments continue to work unchanged.

Every NGX_HTTP_* numeric constant stays defined.

Direct assignment still works

The legacy write path remains functional and is never removed.

ABI stable

No struct reordering and no module-layout changes.

No module rewrites

Existing and third-party modules need no changes to keep compiling.
