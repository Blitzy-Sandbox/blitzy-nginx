# Refactoring Decision Log

This log records every non-trivial decision made during the nginx HTTP status-code registry refactor, which centralizes status handling behind `ngx_http_status_set()` and `ngx_http_status_reason()` backed by a static `ngx_http_status_def_t` registry. Per the Explainability rule, the rationale for each decision is captured in this document rather than in code comments. Deviations from a literal reading of the requirements are flagged explicitly as rows `(a)` through `(e)`. The baseline for this refactor is nginx 1.29.5.

## Decisions

The table below enumerates each non-trivial decision, the alternatives that were considered, the rationale, and the residual risk. Rows `(a)`–`(e)` are the mandatory deviation records; the remaining rows document the other significant design choices.

| Decision | Alternatives | Rationale | Risk |
| --- | --- | --- | --- |
| **(a) Deviation — `CHANGES` created, not updated.**<br>Create a new `CHANGES` file in nginx changelog format instead of editing an existing one. | Skip the changelog entry; fold the note into `README.md`; wait for an upstream `CHANGES` to appear. | Both `CHANGES` and `CHANGES.ru` are **absent** from this trimmed `blitzy-nginx` fork, so the prompt's "UPDATE `CHANGES`" has no target; creating the file in canonical nginx changelog format satisfies the intent and preserves the change trail. Verified: neither file exists at the repository root. | **Low** — a new changelog file cannot break the build; only a mild risk of format drift from upstream nginx conventions. |
| **(b) Deviation — central choke-point validation, not per-`return` edits.**<br>Enforce validation at **three choke-points**: `ngx_http_status_set()` (direct path), the `special_response` `err_status` funnel, and the header-filter emission point. | Rewrite every `return NGX_HTTP_*` to call the API; instrument only `ngx_http_finalize_request()`; do not validate return-based codes at all. | The three status paths — direct assignment, return-based propagation, and the upstream copy — all converge on the status field or its rendering, so instrumenting the seams achieves the "all status flows through the registry" goal with bounded, low-risk edits while leaving the 100+ `return NGX_HTTP_*` statements untouched. | **Medium→Low** — a path bypassing all three seams would be unvalidated; mitigated because the finalize / error-page / header-filter chain covers the render path universally. |
| **(c) Deviation — build wiring in `auto/modules`, not `auto/sources`.**<br>Add `src/http/ngx_http_status.c` to the HTTP core `ngx_module_srcs` (`HTTP_SRCS`) and `src/http/ngx_http_status.h` to `ngx_module_deps` (`HTTP_DEPS`) in `auto/modules`. | Add the pair to `auto/sources` as the AAP literally stated; create a separate dynamic module. | In this tree the core HTTP srcs and deps live in `auto/modules` (`HTTP_DEPS` is initialized there and the core HTTP block lists `ngx_http_request.c`, `ngx_http_special_response.c`, and the like), whereas `auto/sources` only carries specialized subsets (`HTTP_FILE_CACHE_SRCS`, `HTTP_HUFF_SRCS`); placing the new pair in `auto/modules` matches the real layout so it compiles and links with the HTTP core. | **Low** — documented deviation from a literal AAP reading; verified against the actual `auto/` layout. |
| **(d) Deviation from defaults — validation default OFF.**<br>`--with-http_status_validation` defaults **OFF** (`HTTP_STATUS_VALIDATION=NO`); strict validation is compiled in only when explicitly enabled, gated by `#ifdef NGX_HTTP_STATUS_VALIDATION`. | Default ON; a runtime directive toggle; an always-on standard mode. | Guarantees the default shipped binary is **byte-identical** to current behavior — unchanged wire output, preserved graceful binary upgrade (`kill -USR2`), and unchanged `nginx.conf` semantics — and the strict path carries zero runtime cost when it is not compiled in. | **Low** — the feature is dormant by default; the only risk is operators forgetting to enable it, mitigated by the migration guide. |
| **(e) Deviation — upstream guarded pass-through.**<br>Convert the upstream status copy in `ngx_http_upstream.c` (`r->headers_out.status = u->headers_in.status_n;` plus the `status_line` copy) to a **guarded** `ngx_http_status_set()` that guards on `r->upstream` and passes backend codes through **unvalidated** (log-only at most). | Validate upstream codes strictly; leave the raw assignment unconverted; normalize non-standard backend codes. | The prompt prohibits transforming status during upstream proxying, so non-standard backend codes must pass through **byte-for-byte**; the upstream path therefore skips strict range rejection. | **Medium→Low** — mis-guarding could reject valid backend codes; mitigated by the explicit `r->upstream` guard and a log-only policy on this path. |
| **Registry as a static O(1) array (under 1 KB, read-only after init).**<br>A single static `ngx_http_status_def_t[]` indexed by direct array offset, read-only after pre-fork initialization. | A hash map; a dynamic `ngx_array_t` with runtime mutation; per-worker copies. | A direct O(1) offset with no hashing or search honors the "never optimize the registry beyond a static array" constraint and the sub-10-CPU-cycle, sub-2%-latency budget; read-only shared state is lock-free across workers with no thread-local storage; it generalizes the existing `ngx_http_status_lines[]` idiom. | **Low** — must stay under 1 KB per worker and bounds-check every index. |
| **Retain all 45 `NGX_HTTP_*` constants.**<br>Keep every existing `NGX_HTTP_*` numeric constant defined and add the registry additively. | Replace the constants with registry lookups; deprecate or rename them. | Full source-level backward compatibility — third-party modules and existing call sites keep compiling, there is zero import churn, and direct `r->headers_out.status` assignment remains functional. | **Low** — only mild duplication between the constants and the registry entries. |
| **Feature naming to avoid collision.**<br>Name the switch `--with-http_status_validation` and the files `ngx_http_status.c` / `ngx_http_status.h`, distinct from the pre-existing, source-absent `ngx_http_status_module` / `HTTP_STATUS` build variable and its `--without-http_status_module` switch. | Reuse `--with-http_status_module`; name the files `ngx_http_status_module.c`. | The build already defines an unused `HTTP_STATUS=NO` referencing an NGINX-Plus-only source file that is absent from this open-source tree, so a distinct name prevents conflation and build breakage. | **Low** — clear separation, documented here and in the migration guide. |
| **Reason phrase single source.**<br>Make `ngx_http_status_reason()` the single source of status text; the header filter, the `err_status` funnel, and the HTTP/2 and HTTP/3 serializers all delegate to it, while the private `ngx_http_status_lines[]` offset table is migrated/retired and the `status_line.len` fast-path is retained. | Keep the private offset table; duplicate the reason text per consumer. | A single read seam (Facade) removes the three independent owners of reason knowledge and seeds identical phrases (for example "200 OK" and "404 Not Found"), so wire output is unchanged. | **Medium→Low** — reason strings must match byte-for-byte; mitigated by seeding from the existing table and preserving the fast-path. |
| **Preserve custom error-page HTML tables.**<br>Leave the per-code HTML tables (`ngx_http_error_301_page` through `ngx_http_error_411_page`) in `ngx_http_special_response.c` verbatim; the funnel only calls `ngx_http_status_reason()` for the default reason phrase. | Generate the error HTML from the registry; move the HTML into the registry. | The prompt requires the custom error-page generation behavior to be preserved exactly, and `error_page 500 502 503 504 /50x.html` in `conf/nginx.conf` must remain functional, so reason delegation must not alter error-page **selection** — only the **source** of the default reason string. | **Low** — error-page selection logic is untouched. |
| **RFC 9110-grounded validation range and class flags.**<br>Seed the registry and validation logic from RFC 9110 §15 with a 100–599 baseline range and per-class flags (`NGX_HTTP_STATUS_CACHEABLE`, `_CLIENT_ERROR`, `_SERVER_ERROR`, `_INFORMATIONAL`) plus an `rfc_section` back-reference; each API function is capped at 50 lines or fewer, excluding comments. | Ad-hoc per-module range checks; no class metadata. | Grounds compliance validation in the current authoritative HTTP specification (RFC 9110 "HTTP Semantics") and keeps functions small and auditable. | **Low** — the registry seeds a §15 subset while all `NGX_HTTP_*` constants remain defined regardless. |
