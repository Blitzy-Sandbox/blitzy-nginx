# Refactoring Decision Log

This log records every non-trivial decision made during the nginx HTTP status-code registry refactor, which centralizes status handling behind `ngx_http_status_set()` and `ngx_http_status_reason()` backed by a static `ngx_http_status_def_t` registry. Per the Explainability rule, the rationale for each decision is captured in this document rather than in code comments. Deviations from a literal reading of the requirements are flagged explicitly as rows `(a)` through `(g)`. The baseline for this refactor is nginx 1.29.5.

## Decisions

The table below enumerates each non-trivial decision, the alternatives that were considered, the rationale, and the residual risk. Rows `(a)`–`(g)` are the mandatory deviation records; the remaining rows document the other significant design choices.

| Decision | Alternatives | Rationale | Risk |
| --- | --- | --- | --- |
| **(a) Deviation — `CHANGES` created, not updated.**<br>Create a new `CHANGES` file in nginx changelog format instead of editing an existing one. | Skip the changelog entry; fold the note into `README.md`; wait for an upstream `CHANGES` to appear. | Both `CHANGES` and `CHANGES.ru` are **absent** from this trimmed `blitzy-nginx` fork, so the prompt's "UPDATE `CHANGES`" has no target; creating the file in canonical nginx changelog format satisfies the intent and preserves the change trail. Verified: neither file exists at the repository root. | **Low** — a new changelog file cannot break the build; only a mild risk of format drift from upstream nginx conventions. |
| **(b) Deviation — central choke-point validation, not per-`return` edits.**<br>Enforce validation at **three choke-points**: `ngx_http_status_set()` (direct path), the `special_response` `err_status` funnel, and the header-filter emission point. | Rewrite every `return NGX_HTTP_*` to call the API; instrument only `ngx_http_finalize_request()`; do not validate return-based codes at all. | The three status paths — direct assignment, return-based propagation, and the upstream copy — all converge on the status field or its rendering, so instrumenting the seams achieves the "all status flows through the registry" goal with bounded, low-risk edits while leaving the 100+ `return NGX_HTTP_*` statements untouched. | **Medium→Low** — a path bypassing all three seams would be unvalidated; mitigated because the finalize / error-page / header-filter chain covers the render path universally. |
| **(c) Deviation — build wiring in `auto/modules`, not `auto/sources`.**<br>Add `src/http/ngx_http_status.c` to the HTTP core `ngx_module_srcs` (`HTTP_SRCS`) and `src/http/ngx_http_status.h` to `ngx_module_deps` (`HTTP_DEPS`) in `auto/modules`. | Add the pair to `auto/sources` as the AAP literally stated; create a separate dynamic module. | In this tree the core HTTP srcs and deps live in `auto/modules` (`HTTP_DEPS` is initialized there and the core HTTP block lists `ngx_http_request.c`, `ngx_http_special_response.c`, and the like), whereas `auto/sources` only carries specialized subsets (`HTTP_FILE_CACHE_SRCS`, `HTTP_HUFF_SRCS`); placing the new pair in `auto/modules` matches the real layout so it compiles and links with the HTTP core. | **Low** — documented deviation from a literal AAP reading; verified against the actual `auto/` layout. |
| **(d) Deviation from defaults — validation default OFF.**<br>`--with-http_status_validation` defaults **OFF** (`HTTP_STATUS_VALIDATION=NO`); strict validation is compiled in only when explicitly enabled, gated by `#ifdef NGX_HTTP_STATUS_VALIDATION`. | Default ON; a runtime directive toggle; an always-on standard mode. | Guarantees the default shipped binary is **byte-identical** to current behavior — unchanged wire output, preserved graceful binary upgrade (`kill -USR2`), and unchanged `nginx.conf` semantics — and the strict path carries zero runtime cost when it is not compiled in. | **Low** — the feature is dormant by default; the only risk is operators forgetting to enable it, mitigated by the migration guide. |
| **(e) Deviation — upstream guarded pass-through.**<br>Convert the upstream status copy in `ngx_http_upstream.c` (`r->headers_out.status = u->headers_in.status_n;` plus the `status_line` copy) to a **guarded** `ngx_http_status_set()` that guards on `r->upstream` and passes backend codes through **unvalidated** (log-only at most). | Validate upstream codes strictly; leave the raw assignment unconverted; normalize non-standard backend codes. | The prompt prohibits transforming status during upstream proxying, so non-standard backend codes must pass through **byte-for-byte**; the upstream path therefore skips strict range rejection. | **Medium→Low** — mis-guarding could reject valid backend codes; mitigated by the explicit `r->upstream` guard and a log-only policy on this path. |
| **Registry as a static O(1) array (under 1 KB, read-only after init).**<br>A single static `ngx_http_status_def_t[]` indexed by direct class-offset arithmetic, read-only after pre-fork initialization. Each row is a **compact 16-byte layout** — `const char *line` plus four `uint16_t` fields (`line_len`, `code`, `flags`, `rfc_section`) — so the 54-row table measures **864 bytes** (`0x360`), comfortably under the 1 KB budget. | A hash map; a dynamic `ngx_array_t` with runtime mutation; per-worker copies; a wider row built from a 16-byte `ngx_str_t` line plus a `const char *rfc_section` string, which measured 1 296 bytes and breached the budget. | A direct O(1) offset with no hashing or search honors the "never optimize the registry beyond a static array" constraint and the sub-10-CPU-cycle, sub-2%-latency budget; read-only shared state is lock-free across workers with no thread-local storage; it generalizes the existing `ngx_http_status_lines[]` idiom. The compact row interns the full precomputed wire status line (`"NNN reason"`, e.g. `"200 OK"`) as a `const char *` / `uint16_t` length pair and packs `rfc_section` as a `uint16_t` into the row's existing alignment padding, so all four metadata fields — including the per-code RFC back-reference — fit within 16 bytes and keep the table at 864 bytes. | **Low** — must stay under 1 KB per worker and bounds-check every index; the measured 864 bytes leaves ample margin. |
| **Retain all 45 `NGX_HTTP_*` constants.**<br>Keep every existing `NGX_HTTP_*` numeric constant defined and add the registry additively. | Replace the constants with registry lookups; deprecate or rename them. | Full source-level backward compatibility — third-party modules and existing call sites keep compiling, there is zero import churn, and direct `r->headers_out.status` assignment remains functional. | **Low** — only mild duplication between the constants and the registry entries. |
| **Feature naming to avoid collision.**<br>Name the switch `--with-http_status_validation` and the files `ngx_http_status.c` / `ngx_http_status.h`, distinct from the pre-existing, source-absent `ngx_http_status_module` / `HTTP_STATUS` build variable and its `--without-http_status_module` switch. | Reuse `--with-http_status_module`; name the files `ngx_http_status_module.c`. | The build already defines an unused `HTTP_STATUS=NO` referencing an NGINX-Plus-only source file that is absent from this open-source tree, so a distinct name prevents conflation and build breakage. | **Low** — clear separation, documented here and in the migration guide. |
| **Status-line and reason single source.**<br>Make the registry the single source of status text. The **header filter is the sole wire-status-line seam**: it obtains the full precomputed wire status line from `ngx_http_status_line()` and emits it with one `ngx_copy`, the private `ngx_http_status_lines[]` offset table is retired, and the caller-supplied `status_line.len` fast-path is retained. `ngx_http_status_reason()` is the single source of the **bare** reason phrase and is **additionally consumed** by `ngx_http_special_response_handler()`, but only for a debug-level diagnostic — it never sets the wire status line (the header filter does). The **HTTP/2 and HTTP/3 serializers emit a numeric `:status` pseudo-header only** — HTTP/2 (HPACK) and HTTP/3 (QPACK) carry no textual reason phrase — so they correctly do **not** call either accessor. | Keep the private offset table; duplicate the status text per consumer; force a synthetic reason phrase into the HTTP/2 and HTTP/3 `:status`. | A single read seam (Facade) removes the independent owners of status-line knowledge on the HTTP/1.x path. The registry stores the same combined wire literals the offset table shipped — `ngx_http_status_line(200)` returns "200 OK", `line(404)` returns "404 Not Found" — so the header filter reproduces the identical wire status line with a single copy and no per-response formatting; `ngx_http_status_reason()` derives the bare phrase ("OK", "Not Found") by skipping the invariant four-character "NNN " prefix for the diagnostic. HTTP/1.x wire output is therefore unchanged. HTTP/2 and HTTP/3 have no reason phrase to source, so leaving them numeric-only preserves their wire format exactly. | **Medium→Low** — status lines must match byte-for-byte; mitigated by seeding from the existing table and preserving the fast-path. |
| **Preserve custom error-page HTML tables.**<br>Leave the per-code HTML tables (`ngx_http_error_301_page` through `ngx_http_error_507_page`) in `ngx_http_special_response.c` verbatim; the funnel only calls `ngx_http_status_reason()` for the default reason phrase. | Generate the error HTML from the registry; move the HTML into the registry. | The prompt requires the custom error-page generation behavior to be preserved exactly, and `error_page 500 502 503 504 /50x.html` in `conf/nginx.conf` must remain functional, so reason delegation must not alter error-page **selection** — only the **source** of the default reason string. | **Low** — error-page selection logic is untouched. |
| **RFC 9110-grounded validation range, class flags, and per-code section reference.**<br>Seed the registry and validation logic from RFC 9110 §15 with a 100–599 baseline range and per-class flags (`NGX_HTTP_STATUS_CACHEABLE`, `_CLIENT_ERROR`, `_SERVER_ERROR`, `_INFORMATIONAL`); each API function is capped at 50 lines or fewer, excluding comments. Each row **also carries a per-code `rfc_section` back-reference** to the defining RFC 9110 §15 subsection, packed as a `uint16_t` `(subsection << 8) | item` (for example 200 §15.3.1 → `0x0301`, 404 §15.5.5 → `0x0505`, 500 §15.6.1 → `0x0601`); codes not defined in RFC 9110 §15 (for example 429 from RFC 6585, 507 from RFC 4918, and the gap rows) store `NGX_HTTP_STATUS_RFC_NONE` (`0`). | Ad-hoc per-module range checks; no class metadata; storing the reference as a `const char *rfc_section` string; attaching the reference only by class comment. | Grounds compliance validation in the current authoritative HTTP specification (RFC 9110 "HTTP Semantics") and keeps functions small and auditable. Encoding the section reference as a `uint16_t` satisfies the AAP's per-code `rfc_section` requirement **while fitting inside the row's existing 8-byte alignment padding**, so the 54-row table stays at 864 bytes; a `const char *` reference would instead have widened each row to 24 bytes (1 296 bytes total) and breached the firm sub-1 KB budget. The field is functional rather than dead metadata: strict-mode `ngx_http_status_check()` decodes it into `15.<subsection>.<item>` form when logging an RFC 9110 interaction violation. | **Low** — the registry seeds a §15 subset while all `NGX_HTTP_*` constants remain defined regardless; non-§15 codes carry `0`, documented as "no RFC 9110 §15 reference". |
| **(f) Deviation — registry finalization declared in `ngx_http.h`, invoked from `preconfiguration`.**<br>Declare `ngx_http_status_init(ngx_conf_t *cf)` in `src/http/ngx_http.h` and call it from `ngx_http_core_preconfiguration()` (before `ngx_http_variables_add_core_vars()`), during the configuration phase and before the first worker fork. | Declare it in `ngx_http_request.h` (as a literal reading of the finding suggested); call it from a per-request path; leave it uncalled. | `ngx_http_request.h` holds only types and constants — the prototypes for `ngx_http_request.c` functions (for example `ngx_http_init_connection`, `ngx_http_create_request`) already live in `ngx_http.h`, which also includes `ngx_http_status.h`. Declaring the initializer there matches the tree's real prototype layout and makes it visible to the core module; `preconfiguration` guarantees a single pre-fork invocation. | **Low** — verified the symbol is defined in `ngx_http_request.o` and referenced (`U`) from `ngx_http_core_module.o`; runs once at config time, never per request. |
| **(g) Deviation — per-worker status-class counters, gated behind the validation flag.**<br>Maintain `ngx_atomic_t ngx_http_status_counters[]` (1xx–5xx plus a validation-rejections slot) incremented inside `ngx_http_status_set()`, and surface them as labeled `nginx_status_*_total` lines appended to the `stub_status` payload. **Both the counter increment and the six metric lines are compiled in only under `--with-http_status_validation`** (`#if (NGX_HTTP_STATUS_VALIDATION)`): in the default build the increment is a no-op and `stub_status` emits exactly the historical four lines byte-for-byte; the validation build additionally emits the six metric lines. | Aggregate counters in shared memory across workers; add a new metrics module; emit the counters **unconditionally** on the default `stub_status` endpoint (the original CP5 approach, which broke byte-identity); emit them on a separate endpoint. | Reuses nginx's existing lock-free atomic-counter idiom (as used by `ngx_stat_*`) with no new locks, no thread-local storage, and no event-loop edits, satisfying the Observability rule while honoring the "increment in `ngx_http_status_set()`" directive. Gating the counting and emission behind the validation flag is what preserves the master byte-identical invariant for the default build — the CP5 review correctly flagged the earlier unconditional emission as a regression, and the endorsed remedy was to place the metrics behind an opt-in build flag. Counters are **per worker** (not shared-memory aggregated) and count **status-set operations**. | **Low** — default `stub_status` output is byte-identical (runtime-verified: default = 4 lines, validation = 10 lines); the count guard rejects out-of-range indices so a non-standard code can never write out of bounds. |
| **Strict stateful validation checks.**<br>Under `#if (NGX_HTTP_STATUS_VALIDATION)`, `ngx_http_status_check()` warns when an informational (1xx) status follows an already-final status and debug-logs when one final status replaces another, using the current `r->headers_out.status` as the prior-state cursor. | Add a new per-request state field for prior status; skip the interaction checks and validate range only. | RFC 9110 §15 requires 1xx to precede the final status and a single final status; reusing the existing `r->headers_out.status` field as the prior-state cursor avoids any ABI/struct-layout change (Constraint C-007) while still catching the interaction violations. | **Low** — checks are compiled out entirely in the default build; no new struct field. |
| **Header-filter exact status-line sizing.**<br>When the registry supplies a status line, size the status-line buffer as `ngx_http_status_line(status).len` — the exact byte length of the precomputed `"NNN reason"` literal; when it does not, retain the `NGX_INT_T_LEN + 1` numeric-fallback sizing. | Keep a wider `NGX_INT_T_LEN + 1 + reason.len` estimate for all codes; compute the digit count dynamically. | The registry stores the full combined wire line, so the reservation equals the bytes the single `ngx_copy` actually emits, eliminating the per-response over-allocation flagged in review while the fallback path stays safe for unusual values. | **Low** — exact for registry codes; verified no truncation or under-allocation at runtime for 200/301/404/500. |
| **`$request_id` indexing for stable log correlation.**<br>Reserve the `$request_id` variable index once during configuration via `ngx_http_status_log_init()` (invoked from `ngx_http_status_init()`), caching the slot in a file-scope `ngx_int_t`; `ngx_http_status_log()` then reads the request's value through `ngx_http_get_indexed_variable()`, falling back to a by-name lookup only if indexing did not run. | Look the variable up by name on every call with `ngx_http_get_variable()`; or add a new per-request field to hold the id. | A by-name lookup is cached only when the variable is already indexed (for example when it appears in a `log_format`); otherwise it regenerates a fresh value on each call, so the two log lines of a single rejected request — the rejection diagnostic and the caller's failure log — carried different ids. Reserving the index at configuration time yields one stable id per request that also equals the access-log `$request_id`, and the index subsystem returns the shared slot when the operator already references `$request_id`. No new struct field is introduced (Constraint C-007), and the id is computed lazily only when a status log actually fires, so the default happy path is unaffected. | **Low** — default wire output stays byte-identical; verified at runtime that the two log lines share one id and that it matches the access-log `$request_id`. |
| **Header filter byte-identity — CP5 finding proven a false positive.**<br>The CP5 review flagged the HTTP/1.x header filter as changing wire output for in-range gap statuses (203, 205, 305, 306, 407, 417, 506), asserting the original copied zero bytes and never wrote the numeric code. After tracing the original `07a11cf77` source, the finding was determined to be incorrect and **no byte-identity change** was made on that basis. (The header filter *was* later modified for the F-PERF-1 performance fix — see the F-PERF-1 row below — which restored the single-copy render path and was independently re-verified to keep wire output byte-identical across all codes.) | Apply the suggested "fix" (render gap rows as empty); rewrite the status-line resolution. | The original filter's `if (status_line && status_line->len == 0) { status_line = NULL; }` block routes every `ngx_null_string` gap row to the numeric `"%03ui "` writer, so the original already emitted `"203 "` for gap codes — identical to the registry path. This was proven with an exhaustive byte-level harness comparing the original offset-table logic against `ngx_http_status_reason()` for **all codes 0–1023**, which reported zero mismatches. Applying the suggested change would have *introduced* a regression by emitting `"HTTP/1.1 \r\n"` (no numeric code) for gap statuses. | **Low** — the CP5 concern needed no code change; byte-identity is machine-proven across the full code space and re-verified after the F-PERF-1 render change. |
| **Executive-deck dependency and Mermaid security hardening.**<br>Pin Mermaid to a non-vulnerable release and initialize it with a hardened `securityLevel` in `docs/presentation/executive_summary.html`. | Keep Mermaid 11.4.0 with `securityLevel: 'loose'`; drop the embedded diagrams; render diagrams as static images. | Mermaid `>= 11.0.0-alpha.1, < 11.15.0` is affected by CVE-2026-41150 / GHSA-6m6c-36f7-fhxh (a Gantt-diagram infinite-loop DoS), so 11.4.0 was upgraded to the patched 11.15.0. `securityLevel: 'loose'` allows arbitrary HTML/JS in diagram labels; because the deck's diagrams are static first-party content that only needs `<br/>` line breaks, the level was tightened to `'antiscript'` (permits benign HTML, strips scripts). The AAP-pinned `reveal.js@5.1.0` and `lucide@0.460.0` are not flagged by advisories and are kept. | **Low** — the deck renders identically after the bump; the tighter security level removes the script-execution surface without affecting the static diagrams. |
| **QA finding F-PERF-1 — precompute the combined status line to restore the single-copy hot path.**<br>Store the full `"NNN reason"` wire literal in each registry row (`line`/`line_len`) and expose it through `ngx_http_status_line()`, so the HTTP/1.x header filter emits the status line with a single `ngx_copy` — exactly as stock nginx's `ngx_http_status_lines[]` table did — instead of formatting `ngx_sprintf("%03ui ", status)` per response and then copying the bare reason. | Keep the reason-only registry and the per-response `"%03ui "` prepend (the state that triggered F-PERF-1); render the three digits by hand into the buffer; add a second, parallel combined-line table alongside the reason-only rows. | QA report 4 measured the reason-only + per-response `ngx_sprintf` path exceeding the < 2% latency budget on a `return 200;` endpoint (reproduced here at **+2.26% CPU-time/req** vs. stock). Interning the combined line and copying it once removes the per-response formatting from the known-code hot path; an isolated microbenchmark linking the real `ngx_string.o` measured the render at **20.98 ns/op** (sprintf+copy) → **3.88 ns/op** (single copy), an **81.5%** reduction (≈17 ns, ≈51 cycles at 3 GHz). The registry stays the single authority: `ngx_http_status_reason()` still returns the bare phrase by skipping the invariant four-character `"NNN "` prefix, so no second table and no duplicated text is introduced; the row stays 16 bytes (a `const char *` plus a `uint16_t` length, whether it names the phrase or the full line), so the table remains 864 bytes. | **Low** — restores stock's exact mechanism; re-verified byte-identical to stock across all 69 tested codes (36 registry + 18 gap + 15 boundary/out-of-range) and the default error bodies, with fixed CPU-time/req at **+0.76%** (within budget), and the `"%03ui "` writer still covers gap/unknown codes as the fallback. |
| **QA finding Info-1 — uniform 500 for a rejected local `err_status`.**<br>In `ngx_http_send_header()` (`ngx_http_core_module.c`), when `ngx_http_status_set(r, r->err_status)` is rejected, log the failure and fall back to `ngx_http_status_set(r, NGX_HTTP_INTERNAL_SERVER_ERROR)` through the same sanctioned write path, so a rejected code never reaches the wire as a degenerate `"000"` status line. | Leave the status unset (the pre-fix behavior, which rendered `"000 "` under strict validation); abort the connection; special-case the reason string in the header filter. | Report 2 Info-1 observed that under `--with-http_status_validation` a locally generated out-of-range `err_status` (for example a `return 999;`) was rejected but then rendered as `"000"`. Routing the fallback through `ngx_http_status_set()` keeps a single write seam and yields a clean, uniform `500 Internal Server Error`. The fallback is **unreachable for upstream requests** — `ngx_http_status_set()` returns `NGX_OK` unconditionally when `r->upstream` is set (guarded pass-through), so backend status is never affected — and it is a dead branch in the default build, where local validation never fails, preserving byte-identity. | **Low** — no-op in the default build; re-verified in the validation build that `return 99/600/999` render `500` with a logged, request-id-correlated rejection, and that the upstream pass-through stays byte-for-byte for standard, non-standard, and out-of-range (999) backend codes in both build variants. |
